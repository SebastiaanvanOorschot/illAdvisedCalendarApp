# Contributing

Short, actionable conventions for adding to this codebase. See [ARCHITECTURE.md](ARCHITECTURE.md)
for how the system is put together; this document is about how to add to it without
reintroducing the things it was refactored away from (duplication, controllers touching
the DB directly, AutoMapper-style magic, etc.).

## Backend — adding a new endpoint

Follow the existing layer order, illustrated by `UserPreferencesController` /
`UserPreferencesService` / `UserPreferencesDto`:

```
Controller → Service → DTOs → Mapping
```

1. **Controller** (`Controllers/`) — HTTP only. `[Authorize]`, `[ApiController]`,
   `[Route("api/[controller]")]`. Extract the user id via a `GetCurrentUserId()` helper
   reading `ClaimTypes.NameIdentifier` (or `"sub"`) from `User`. Call one service method,
   translate its result to an `IActionResult`/`ActionResult<T>`. **Never inject or touch
   `AgendaDbContext` in a controller.**
2. **Service** (`Services/`) — a concrete class (not an interface — see exception below),
   holding `private readonly AgendaDbContext _context` and all business logic. Register it
   in `Program.cs` with `builder.Services.AddScoped<YourService>();`.
   - Use an interface only when a second implementation or test substitution is realistic
     (see `IRecurrenceService`, `IGoogleCalendarService`). Otherwise a concrete class is
     enough — most services have exactly one implementation.
   - Return a typed result, not exceptions, for expected failure cases: define
     `YourServiceStatus` (`Success`, `NotFound`, `Forbidden`, ...) and a
     `YourServiceResult` / generic `YourServiceResult<T>` with static factories (`Ok(...)`,
     `NotFoundResult()`, ...). The controller switches on `result.Status` to pick the HTTP
     response — see `UserPreferencesService` / `UserPreferencesController` or the
     `EventServiceStatus` switch in [ARCHITECTURE.md](ARCHITECTURE.md#backend-layered-architecture).
3. **DTOs** (`DTOs/`) — plain classes, `Dto` suffix (e.g. `CreateEventDto`). Request DTOs
   contain **only client-settable fields** — never `Id`, `UserId`, `CreatedAt`,
   `UpdatedAt`, or other server-controlled fields (see `CreateEventDto`/`UpdateEventDto`).
   Note: this suffix isn't applied 100% consistently today (`UpdateUserPreferencesRequest`
   is one exception) — use `Dto` for anything new regardless.
4. **Mapping** (`Mapping/`) — a static class, one per feature (`EventMapper`,
   `CalendarSubscriptionMapper`), doing explicit field-by-field assignment between
   `Models/` entities and DTOs. Mappers are **pure**: no `_context` access, no `async`.
   If a mapped field needs data from outside the entity (e.g. owner name, share
   permission), pass it in as a parameter — see `EventMapper.ToWithOwnerDto(e, isOwnEvent,
   permission, subscriptionName)` — don't have the mapper fetch it itself (that's how you
   get N+1 queries).

**Schema changes**: there's no migrations tool. New columns/tables go through
`EnsureCreated()` (fresh DBs) plus an idempotent `ExecuteSqlRaw` in `Program.cs`
(`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, ...) for databases that already
exist — see the block after `db.Database.EnsureCreated()` in `Program.cs` for the current
examples.

## Frontend — conventions

Shared logic belongs in one place — check before writing it again:

| Kind of thing | Location | Example |
|---|---|---|
| Reusable TS types | `src/types/` | `calendar.ts` |
| Static lookup data/constants | `src/constants/` | `eventColors.ts` (`EVENT_COLOR_OPTIONS`) |
| Small helpers (formatting, etc.) | `src/utils/` | `dateFormat.ts` (`formatDate`, `formatTime`) |
| Shared reactive logic | `src/composables/` | `useWeather`, `useAuth`, `useEventOperations` |

- **Styling**: use the CSS custom properties defined on `:root` in `src/css/Style.css`
  (`--color-primary`, `--color-text-muted`, `--color-danger`, ...) — no hardcoded hex
  colors in components. The one exception is data colors (the event/subscription color
  picker) — those live in `constants/eventColors.ts` as actual hex values, not as CSS
  tokens, because they're data the user picks from, not theme colors.
- **API client** (`src/api/agenda-api-swagger.ts`) is generated by NSwag from the
  backend's OpenAPI spec — never hand-edit it. Regenerate after backend DTO/route
  changes.
- **Env vars**: `VITE_`-prefixed, baked in at build time. A new one needs both an entry
  in `.env` for local dev **and** an `ARG`/`ENV` pair in `AgendaFrontend/Dockerfile`
  (see `VITE_API_URL`/`VITE_GOOGLE_CLIENT_ID`) — otherwise it's `undefined` in the
  Railway-built production bundle even though it works locally.

## Before you push

- `dotnet build AgendaApi/AgendaApi.sln` and `yarn build` (in `AgendaFrontend/`, runs
  type-check + build) must both be green. `.github/workflows/ci.yml` runs the same two
  checks on push to `development` and on PR to `master` — check locally first.
- Work on `development`; merging `development` into `master` triggers the Railway deploy
  for both services.

## Working with an AI assistant

Reference this document in prompts ("follow CONTRIBUTING.md") and review the diff for
layer violations and duplicated logic — the build check catches compile errors, not
architecture drift.
